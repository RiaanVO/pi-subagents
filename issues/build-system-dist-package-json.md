# Issue: Build System Gap — dist/package.json and Auto-Compile Reliability

## Context

The UDS system requires `dist/uds-server.js` to exist at runtime (the child process `uds-child.mjs` imports it from `../dist/uds-server.js`). The build process handles this in two ways:

1. **Production**: `npm run build` compiles TypeScript to `dist/`, then creates `dist/package.json` with `{"type":"module"}` so Node.js knows the compiled JS is ESM.

2. **Development**: `ensureUDSServerCompiled()` in `uds-agent-runner.ts` auto-compiles the project on-demand and creates `dist/package.json` if missing.

The gaps:
- If `tsc` is not in `node_modules/.bin`, the auto-compile silently fails (the catch block just ignores it)
- The child gets a cryptic "ENOENT" or module parse error if the compile fails
- `dist/package.json` can become stale if a previous build had a different module type
- The auto-compile compiles the **entire project** (`tsc --project tsconfig.json`) just to get the UDS server — this is overkill and slow

## Files

- `src/uds-agent-runner.ts` — `ensureUDSServerCompiled()` (auto-compile logic)
- `package.json` — build script (runs `check-uds-imports.mjs` then `tsc`)
- `src/uds-child.mjs` — imports from `../dist/uds-server.js`
- `src/check-uds-imports.mjs` — build-time validation

## Decisions to Make

- Should auto-compile fall back to a helpful error message instead of silently failing?
- Should we create a separate `tsconfig.uds.json` to only compile the UDS files?
- Should `dist/package.json` be generated by the build step and not at runtime?
- Should `uds-child.mjs` import from `../dist/uds-server.js` or from the source `.ts` file (with a different import path for dev vs prod)?

## Detailed Research Report

### 1. Current Build Flow (Step by Step)

#### Production Build (`npm run build`)

```
rm -rf dist/                                # ← Delete entire dist/
node src/check-uds-imports.mjs              # ← Validate imports (runs AFTER dist/ deleted)
tsc                                         # ← Full project compile (defaults to tsconfig.json)
echo '{"type":"module"}' > dist/package.json # ← Set ESM mode
```

**Step 1: `rm -rf dist/`** — Wipes the entire dist/ directory clean. This ensures no stale artifacts remain.

**Step 2: `node src/check-uds-imports.mjs`** — Runs the UDS import checker **after** dist/ has been deleted. This script:
- Checks ESM compatibility of `.mjs` files (checks for CJS-only `homedir`/`tmpdir` from `node:path`)
- Checks **file existence** of referenced modules:
  - `src/uds-child.mjs` — must exist (source file, checked as error)
  - `dist/uds-server.js` — checks exists, but gives **warning** (not error) for dist files
  - `dist/agent-runner.js`, `dist/agent-types.js`, `dist/env.js`, `dist/types.js`, `dist/usage.js` — all checked with warnings
- Scans all `.ts` files for `fork("...uds-child.mjs")` calls to verify targets exist

**BUG: This check runs AFTER `rm -rf dist/`** — so it will always warn about missing `dist/uds-server.js`, `dist/agent-types.js`, etc. The warnings are non-fatal, but it means the check provides no useful signal during the build. It's essentially a no-op during `npm run build`.

**Step 3: `tsc`** — Compiles the **entire project** (all ~35 TypeScript files in `src/`) to `dist/`. This includes:
- `uds-server.ts` (the UDS server)
- `uds-agent-runner.ts` (the parent runner)
- `agent-manager.ts`, `agent-runner.ts`, `agent-types.ts`, etc.
- All workflow, ui, and utility modules

The `tsconfig.json` settings:
```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ES2022",
    "moduleResolution": "bundler",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "outDir": "dist",
    "rootDir": "src",
    "declaration": true
  },
  "include": ["src/**/*.ts"]
}
```

Key implications:
- `"moduleResolution": "bundler"` — uses Node.js "bundler" resolution (Node 19.8+), which is stricter about file extensions
- `"rootDir": "src"` — all source files from `src/` get compiled preserving the directory structure
- `"declaration": true` — generates `.d.ts` files alongside `.js` files (dist/ has 79+ files total)

**Step 4: `echo '{"type":"module"}' > dist/package.json`** — Creates `dist/package.json` with `{"type":"module"}`. This is **essential** because Node.js requires `package.json` with `"type": "module"` to treat `.js` files as ESM in a directory that doesn't inherit from a parent `"type": "module"`.

#### Development Auto-Compile (`ensureUDSServerCompiled()`)

```typescript
function ensureUDSServerCompiled(): void {
  try { accessSync(UDS_SERVER_PATH); return; } catch { /* missing — compile below */ }
  try { accessSync(TSC_PATH); } catch { return; }  // ← silently exits if tsc missing!
  
  try {
    execSync(`"${TSC_PATH}" --project tsconfig.json --outDir dist --skipLibCheck`, {
      cwd: projectRoot,
      stdio: "ignore",
    });
    writeFileSync(join(projectRoot, "dist", "package.json"), '{"type":"module"}');
  } catch {
    // Compilation failed silently — the child will get its own error.
  }
}
```

**Flow:**
1. Check if `dist/uds-server.js` already exists → if yes, return immediately (fast path)
2. Check if `node_modules/.bin/tsc` exists → if **no**, return **silently** (no compile attempted)
3. Run `tsc --project tsconfig.json --outDir dist --skipLibCheck`
4. Write `dist/package.json` with `{"type":"module"}`
5. If compilation fails → **silently swallow the error**, child gets own error

#### Critical Gap: The Auto-Compile Compiles the Whole Project

The comment in the code says:
> "Compiling just a few files wouldn't resolve their transitive deps."

This is technically true because `uds-agent-runner.ts` (the parent) imports from:
- `./agent-types.js`
- `./agent-runner.js`
- `./env.js`
- `./types.js`
- `./usage.js`

But **`uds-server.ts`** (the child's core dependency) does **not** import any internal files! It only imports:
- `node:net`, `node:fs` (Node builtins)
- `@earendil-works/pi-coding-agent` (peer dependency)
- `@earendil-works/pi-ai` (peer dependency)

However, the parent (`uds-agent-runner.ts`) does import internal modules because it needs `getAgentConfig`, `getToolNamesForType`, etc. to configure the child process. So the **parent** does need the full project compiled. But the **child** (`uds-child.mjs`) only needs `uds-server.ts` compiled.

### 2. Failure Modes (What Can Go Wrong and How Silently)

#### Failure Mode 1: `tsc` Not in `node_modules/.bin`

**What happens:** `accessSync(TSC_PATH)` throws → caught → function returns silently → `dist/uds-server.js` doesn't exist → `uds-child.mjs` fails to import → **forked child crashes immediately** → parent sees "Child did not create socket" or "Failed to connect to child socket" error.

**Silence level:** Very high. The parent catches the `tsc` missing, returns, then the child gets an ENOENT on the import. No helpful error message tells the developer "you need to run `npm install` first."

**Detection:** The `check-uds-imports.mjs` would catch this if run separately, but during `ensureUDSServerCompiled()` it's not run.

#### Failure Mode 2: `tsc` Exists But Compilation Fails (TypeScript Errors)

**What happens:** `execSync()` throws → caught → error swallowed → `dist/uds-server.js` doesn't exist → same cascade as above.

**Silence level:** Very high. `stdio: "ignore"` discards all compiler output. Even if `tsc` found errors, the developer gets no feedback.

**Detection:** None in the auto-compile path. Developer must check `npm run typecheck` or `npm run build` separately.

#### Failure Mode 3: `tsc` Exists But Fails at Runtime (Missing `node_modules`)

**What happens:** If peer dependencies (`@earendil-works/pi-coding-agent`, etc.) are not installed, `tsc` may succeed (because `skipLibCheck: true` and module resolution might pass) but the compiled JS will fail at runtime when the child process tries to import those modules.

**Silence level:** High. The child crashes with a module not found error that doesn't clearly point to missing `npm install`.

#### Failure Mode 4: `dist/package.json` Stale or Wrong

**What happens:** If `dist/package.json` is overwritten with `{"type":"commonjs"}` (unlikely but possible via another tool), all `.js` imports in `dist/` will fail with "Cannot use import statement outside a module".

**Silence level:** Medium. The child process will get a module parse error. No clear signal that `dist/package.json` is the problem.

#### Failure Mode 5: `check-uds-imports.mjs` Run After `rm -rf dist/`

**What happens:** The file existence check runs **after** `dist/` has been deleted. All dist/ file checks will produce warnings. The warnings are non-fatal, so the build continues normally.

**Silence level:** Low (warnings are visible), but **the check is misleading** — it reports warnings about files that were intentionally just deleted. This gives a false impression of problems.

#### Failure Mode 6: File Permissions on `dist/`

**What happens:** If `dist/` exists but has wrong permissions, `accessSync(UDS_SERVER_PATH)` may succeed but `writeFileSync(dist/package.json)` could fail (not currently caught in the outer try). Or the child process might not be able to read `dist/uds-server.js`.

**Silence level:** High. Child gets ENOENT or permission denied.

### 3. Proposed Approaches

#### Approach A: Better Error Messaging in `ensureUDSServerCompiled()`

**What changes:**
- When `tsc` is not found: throw a descriptive error with instructions ("Run `npm install` to install TypeScript, or run `npm run build`")
- When compilation fails: log the error to stderr and throw
- Replace `stdio: "ignore"` with `stdio: "inherit"` for compilation errors

**Pros:**
- Minimal code change
- Gives developers actionable feedback
- No structural changes to the build

**Cons:**
- Still compiles the entire project (~35 files) for a single dependency
- The child process still gets errors if auto-compile fails (just with better messages)
- Doesn't solve the root cause

#### Approach B: Dedicated `tsconfig.uds.json` for Standalone UDS Compilation

**What changes:**
- Create `tsconfig.uds.json` that only includes `src/uds-server.ts`
- `ensureUDSServerCompiled()` runs `tsc --project tsconfig.uds.json --outDir dist`
- This would compile just `uds-server.ts` (1 file, ~400 lines) instead of all ~35 files

**Pros:**
- Much faster auto-compile (1 file vs 35 files)
- `uds-server.ts` has no internal imports — only external peer deps
- Cleaner separation of concerns

**Cons:**
- `uds-server.ts` depends on peer packages that may not be resolved from `tsconfig.uds.json`
- May need careful module resolution config
- The parent (`uds-agent-runner.ts`) still needs the full project compiled

#### Approach C: Dual Import Paths (Dev vs Prod)

**What changes:**
- `uds-child.mjs` imports conditionally:
  ```js
  // Dev: import directly from .ts via a loader or transpiler
  // Or: use .mjs source directly if uds-server.ts was written as .mjs
  let UdsServer;
  try {
    UdsServer = (await import("../dist/uds-server.js")).UdsServer;
  } catch {
    // Fallback: compile on demand (current behavior)
    await ensureUDSServerCompiled();
    UdsServer = (await import("../dist/uds-server.js")).UdsServer;
  }
  ```
- Or restructure: write `uds-server` as a `.mjs` file that doesn't need compilation (no TypeScript)

**Pros:**
- Cleaner separation of dev/prod paths
- Can use `.mjs` files that run without compilation in dev

**Cons:**
- Requires rewriting `uds-server.ts` as `.mjs` or adding a runtime transpiler
- Adds complexity to the import logic
- May break bundler resolution

#### Approach D: Inline the UDS Server (No Separate File)

**What changes:**
- Move the UDS server code directly into `uds-child.mjs` or `uds-agent-runner.ts`
- Eliminate the cross-file import entirely

**Pros:**
- Eliminates the entire dist/package.json problem
- No compilation dependency for the child process
- Simplest possible approach

**Cons:**
- UDS server is substantial (~400 lines, complex IPC logic)
- Mixing server and client logic violates separation of concerns
- Harder to test independently

#### Approach E: Pre-Build `dist/package.json` and Ship It

**What changes:**
- Include `dist/package.json` in the published package (already exists in dist/)
- Keep auto-compile for `tsc` compilation, but always create `dist/package.json` at build time
- Remove the runtime `writeFileSync(dist/package.json)` from `ensureUDSServerCompiled()`

**Pros:**
- `dist/package.json` is guaranteed to exist after `npm install`
- Eliminates one runtime concern
- Clean separation: build creates package.json, auto-compile only handles tsc

**Cons:**
- Doesn't solve the silent compile failure
- The file is already shipped (current approach), so this is incremental

### 4. Alternative Import Strategies (Dev vs Prod Paths)

#### Current Pattern: Import from `../dist/`

```js
// uds-child.mjs line 32:
import { UdsServer } from "../dist/uds-server.js";
```

This is a **hard-coded path** to the compiled output. It only works when:
1. `dist/uds-server.js` exists
2. `dist/package.json` has `{"type":"module"}`
3. The path `../dist/uds-server.js` resolves from `uds-child.mjs`'s location

#### Alternative 1: Import from `./` with Extension (Unified Dev/Prod)

If `uds-server.ts` were written as `uds-server.mjs` (no TypeScript), the import could be:
```js
import { UdsServer } from "./uds-server.mjs";
```

**Pros:** Works in both dev (`.mjs` runs directly) and prod (same file)
**Cons:** Requires rewriting in plain JS, losing type safety

#### Alternative 2: Use `package.json` `exports` Field

Add to `package.json`:
```json
{
  "exports": {
    "./uds-server": {
      "import": "./dist/uds-server.js",
      "types": "./dist/uds-server.d.ts"
    }
  }
}
```

Then import as:
```js
import { UdsServer } from "@RiaanVO/pi-subagents/uds-server";
```

**Pros:** Clean API, module resolution is centralized
**Cons:** Still requires dist/ to exist, adds package.json complexity

#### Alternative 3: Dynamic Import with Compile-on-Demand

```js
let UdsServer;
try {
  UdsServer = (await import("../dist/uds-server.js")).UdsServer;
} catch (e) {
  if (e.code === 'MODULE_NOT_FOUND' || e.code === 'ERR_MODULE_NOT_FOUND') {
    // Compile on demand
    await compileUDS();
    UdsServer = (await import("../dist/uds-server.js")).UdsServer;
  } else throw e;
}
```

**Pros:** Graceful degradation, clearer error handling
**Cons:** Slower first run (compile + import), double-import on first run

#### Alternative 4: Symlink from `src/` to `dist/`

```
src/uds-server.mjs → dist/uds-server.js
```

**Pros:** Development import works via `../src/uds-server.mjs`
**Cons:** Requires post-build symlink step, fragile across platforms

#### Alternative 5: ESM Loader for `.ts` Imports

Use Node.js experimental ESM loader to import `.ts` files directly:
```js
import { UdsServer } from "../src/uds-server.ts";
```

**Pros:** No dist/ needed at all
**Cons:** Requires `--experimental-loader` flag, not production-ready, slow

### 5. Similar Patterns in the Codebase

**Internal imports use the `./module-name.js` convention:**
All `.ts` files in `src/` import from each other using `./module-name.js` syntax (the `.js` extension pointing to `.ts` source files). This is the TypeScript + ESM convention where the import path uses `.js` but the actual file is `.ts`.

Examples from `uds-agent-runner.ts`:
```ts
import { getAgentConfig, getConfig, getToolNamesForType } from "./agent-types.js";
import { detectEnv } from "./env.js";
import { resolveDefaultModel } from "./agent-runner.js";
```

These imports work because TypeScript's `moduleResolution: "bundler"` maps `.js` to `.ts` at compile time, and at runtime the `.js` files exist in `dist/`.

**The UDS child is unique** because it crosses the `src/` → `dist/` boundary:
- `uds-child.mjs` is in `src/` but imports from `../dist/uds-server.js`
- All other imports in the codebase stay within `src/` (using `.js` suffix for `.ts` files)

This boundary crossing is the root cause of the entire issue — the child process runs independently and needs the compiled output, but the parent orchestrates the compile.

### 6. Decision Trade-offs

| Approach | Build Speed | Error Clarity | Complexity | Risk |
|----------|------------|---------------|------------|------|
| **A: Better error messaging** | Same (slow) | ✅ High | Low | Low |
| **B: Dedicated tsconfig.uds.json** | ✅ Fast | Same | Medium | Medium (resolv.) |
| **C: Dual import paths** | ✅ Fast (dev) | Medium | High | High |
| **D: Inline UDS server** | ✅ Fastest | Medium | Low | High (architecture) |
| **E: Pre-build dist/package.json** | Same (slow) | Low | Low | Very Low |

#### Key Constraints:
1. **The parent (`uds-agent-runner.ts`) imports internal modules** — it needs `./agent-types.js`, `./agent-runner.js`, etc. So the parent side **always** needs the full project compiled.
2. **The child (`uds-child.mjs`) only imports `uds-server.ts`** — this is standalone, no internal deps.
3. **The auto-compile currently serves both** — one `tsc` call compiles everything, but only the child needs `uds-server.js`.

#### Critical Finding:
The comment "Compiling just a few files wouldn't resolve their transitive deps" is **misleading**. The parent compiles itself as part of the normal module resolution — `uds-agent-runner.ts` is compiled by the parent's own import graph. The auto-compile doesn't need to compile `agent-types.ts` separately; the parent already imports it via `./agent-types.js` and TypeScript resolves it. The auto-compile only needs `uds-server.ts` for the child process.

---

### Recommended Approach

**Recommend: Approach A + Approach E (Minimal, safest)**

1. **Improve error messaging in `ensureUDSServerCompiled()`**:
   - When `tsc` is missing: throw an error with clear instructions
   - When compilation fails: `stdio: "inherit"` so the error is visible
   - Add a check: `if (!existsSync(UDS_SERVER_PATH)) throw new Error(...)` after compile attempt

2. **Keep pre-built `dist/package.json`** (it's already shipped):
   - This is already working — `dist/package.json` is included in the published package
   - The runtime `writeFileSync` is a safety net, but the primary source is the pre-built file

3. **Fix `check-uds-imports.mjs` ordering**:
   - Move the `rm -rf dist/` to AFTER the check, or
   - Have the check skip dist/ existence when run from `npm run build`

**Implementation priority:**
1. **High priority**: Fix silent failure — add clear error messages
2. **Medium priority**: Fix `check-uds-imports.mjs` ordering (move check before rm, or add `--skip-dist-check` flag for build)
3. **Low priority**: Consider dedicated `tsconfig.uds.json` for faster auto-compile
4. **Future**: Consider if the child should use dynamic import with compile-on-demand

**Rationale**: This approach minimizes risk while addressing the most impactful issues (silent failures and misleading checks). It doesn't require architectural changes and can be implemented incrementally.

### Decisions Made

> **Date:** Consulted on 2025-07-15

Four decisions were made through collaborative review. The implemented approach combines the best elements of the recommended strategies.

#### Decision 1: Error Handling — Helpful Messages Instead of Silent Failures

**Choice:** `ensureUDSServerCompiled()` should provide helpful error messages when `tsc` is missing or compilation fails.

**Rationale:** Silent failures are the worst developer experience. When auto-compile fails, the developer must discover the problem indirectly through cryptic child-process errors. Clear, actionable messages dramatically improve debuggability with minimal risk.

**Approach selected:** Approach A (Better Error Messaging)
- When `tsc` is not found: throw a descriptive error with instructions ("Run `npm install` to install TypeScript")
- When compilation fails: use `stdio: "inherit"` so compiler output is visible

#### Decision 2: Dedicated `tsconfig.uds.json` for Faster Auto-Compile

**Choice:** Create a dedicated `tsconfig.uds.json` that only compiles `src/uds-server.ts` (~400 lines) instead of the full project (~35 files).

**Rationale:** The child process only needs `uds-server.ts`, which has no internal dependencies (only Node builtins and peer packages). Compiling the entire project for auto-compile is overkill and makes the dev iteration feel slow.

**Approach selected:** Approach B (Dedicated tsconfig)
- New file: `tsconfig.uds.json` with `include: ["src/uds-server.ts"]`
- `ensureUDSServerCompiled()` uses `--project tsconfig.uds.json` instead of `--project tsconfig.json`

#### Decision 3: Shared Utility for `dist/package.json` Creation

**Choice:** Extract `dist/package.json` creation into a shared utility function used by both the production build script and the auto-compile path.

**Rationale:** Having two separate code paths that write `dist/package.json` is a maintenance risk — they can fall out of sync. A single source of truth ensures consistent behavior.

**Approach selected:** Extract to shared utility (Option A)
- New file: `scripts/create-dist-package-json.mjs` containing the `dist/package.json` creation logic
- Both `package.json` build script and `ensureUDSServerCompiled()` import and call this function

#### Decision 4: Import Path — Keep Current Pattern

**Choice:** Keep `uds-child.mjs` importing from `../dist/uds-server.js`.

**Rationale:** With faster auto-compile (Decision 2), better error handling (Decision 1), and a unified `dist/package.json` approach (Decision 3), the existing import pattern works well. Changing to dynamic import or restructuring adds complexity without meaningful benefit.

**Approach selected:** Keep current
- No change to `uds-child.mjs` import path
- The existing pattern is explicit, simple, and works reliably with the improved auto-compile
